## 2026-04-30 — Flow child-invocation uses `shared_logicflows` (Flow Management) connection reference with `runtimeSource: embedded`

**Decided:** All calls from one child flow to another (e.g. `cch_AgentToolWrapper` → `cch_LogTelemetry`, `cch_IssueDirectLineToken` → `cch_ResolveSecret`) use the **`shared_logicflows` connector** (`/providers/Microsoft.PowerApps/apis/shared_logicflows`) wired through the `cch_FlowManagement` Connection Reference, with `runtimeSource: embedded` in the flow JSON. This is the PAC-unpacked representation of Power Automate's "Run a Child Flow" action when the child is a **solution-aware** flow.

**Why:** Solution-aware child flows (flows whose `name` is registered in `Solution.xml` as type=29 `RootComponent`) can only be invoked via the "Run a Child Flow" action, not via HTTP POST. The `shared_logicflows` / Flow Management connector is the correct connector for this. `runtimeSource: embedded` tells PAC the connection is embedded in the solution rather than a named external connection, which is required for portability across environments.

**Alternatives considered:**
- HTTP trigger on child flows + HTTP call from parent → would work but requires exposing each child flow via an HTTP endpoint with its own connection security, adding surface area and defeating the "child flow" abstraction.
- `shared_logicflows` without `runtimeSource: embedded` → the PAC unpack representation requires `embedded` for in-solution flows; omitting it causes import failures.

**Affects:** Every subsequent Flows-Engineer PR that invokes `cch_LogTelemetry` or `cch_ResolveSecret` must use the same `shared_logicflows` + `cch_FlowManagement` pattern. The connection reference logical name is `cch_FlowManagement`; operators wire it at install time via `install.ps1`.

## 2026-04-30 — Workflow filenames use deterministic GUID prefix `b1e2c3d4-e5f6-4890-abcd-ef12345600NN`

**Decided:** The 4 infrastructure flow JSON files use **deterministic GUIDs** with a fixed prefix (`b1e2c3d4-e5f6-4890-abcd-ef1234560001` through `…0004`) rather than random GUIDs generated by `pac solution clone`. Each file is named `<flowName>-<guid>.json`.

**Why:** `pac solution clone` generates random UUIDs; those UUIDs are embedded in both the filename and internal `operationMetadataId` fields. For flows authored by hand (no running environment to clone from), picking deterministic GUIDs makes the files stable across re-exports, simplifies cherry-picks and diffs, and lets future flows increment the last two hex digits (`…0005`, `…0006`, …) to stay visually distinct. The PAC tooling does not validate GUID format beyond syntactic correctness.

**Alternatives considered:**
- Use real random GUIDs (e.g., `uuidgen`) → stable per initial generation but harder to read in diffs; no benefit over deterministic since the values are internal identifiers only.
- Use sequential integers as names (no GUID) → `pac solution pack` requires GUID-suffixed filenames to resolve workflow identity; omitting them causes import errors.

**Affects:** All subsequent Flows-Engineer PRs should continue the `b1e2c3d4-e5f6-4890-abcd-ef1234560NNN` series (incrementing the last 3 digits: `…005`, `…006`, …). The `operationMetadataId` field inside each flow's trigger should match the file GUID to keep the mapping 1-to-1.

## 2026-04-30 — Flows-Engineer PR #1 ships 6 env var definitions + 2 connection references + schema (cross-role scope expansion)

**Decided:** This PR ships artifacts outside the strict Flows-Engineer scope: **6 environment variable definitions** (`cch_IdAgent*`, `cch_SecretDirectLine*`) and **2 connection references** (`cch_DataverseDefault`, `cch_FlowManagement`) that normally belong to Dataverse-Engineer and Lead respectively, plus **`scripts/lib/AgentToolContract.schema.json`** that is normally Lead/Tester scope. The scope expansion was accepted as part of this PR.

**Why:** Power Automate flows cannot be imported (or validated by PAC) without their connection references and environment variable definitions already present in the solution. Shipping them separately in a prior PR was impractical: the Dataverse-Engineer issue (#5) already shipped the schema baseline; a separate micro-PR for 6 env vars would block this PR unnecessarily. The flow JSON files explicitly reference `cch_DataverseDefault`, `cch_FlowManagement`, and all 6 `cch_IdAgent*/cch_SecretDirectLine*` env vars by logical name — they are compile-time dependencies, not optional additions. `AgentToolContract.schema.json` was referenced in the issue text as "TBD: file lands later, this issue may need to scaffold it," making this PR the natural home.

**Alternatives considered:**
- Ship env vars in a separate Dataverse-Engineer PR first, then open this flows PR → adds a blocking dependency, delays Phase 4 start.
- Ship flow JSONs with placeholder connection reference names → PAC import would fail; the logical names are required at import time.
- Leave `AgentToolContract.schema.json` to a follow-up issue → the schema is needed by the Tier-1 `schema-drift` stub and by every subsequent tool-flow PR; landing it here avoids drift.

**Affects:** Cross-cutting. Establishes the precedent that a role's PR may include **compile-time dependencies** of its primary artifacts even if those dependencies formally belong to another role. The hand-off rule remains: after merge, Dataverse-Engineer owns the lifecycle of these env var definitions; Lead owns the connection reference pattern. Both roles should review changes to these files in future PRs.
