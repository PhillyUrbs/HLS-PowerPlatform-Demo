### 3.1 Scenario
- **Subsector:** Medtech — Continuous Glucose Monitor (CGM) manufacturer
- **Company name:** Contoso Continuum Health (fictitious)
- **Reuse assets:** Net-new fictitious company. **No** Microsoft Cloud for Healthcare data model.
- **Personas (4):** Patient · Endocrinologist (HCP) · Field Clinical Specialist (FCS) · Quality/Complaints Analyst
- **Compliance theme:** Lightweight nods (audit trail, MDR-reportable flag) — **not** a hero theme. No FDA/HIPAA/GxP validation claims.
- **Branding:** Default — Contoso Continuum Health, clinical blue/teal palette. Detailed branding is **Topic 2 — still open**.

### 3.2 Vignettes
- **Count:** 6 modular vignettes (5–10 min each, demoable standalone or chained 1→6).
- **Order (recommended demo order):** 1 → 2 → 3 → 4 → 5 → 6.
- See **Section 7** for full per-vignette specs.

### 3.3 Apps & surfaces
- **Power Apps:** Power Apps **Code App** (React + Vite) — `apps/field-companion/`
- **Power Pages:** Power Pages **Code Site** (React SPA) — `sites/continuum-portal/`
- **Power Automate:** flows live inside the Dataverse solution
- **Copilot Studio:** **3 distinct agents** (see Section 6)
- **UI library:** **Fluent UI v9** (`@fluentui/react-components`), shared between Code App and Pages site
- **Navigation pattern:** Top bar + left nav + content area
- **Screen density:** Medium-high (cards, lists, side panels)
- **Live update animation:** Subtle highlight + slide-in on changed/new rows
- **Accessibility:** WCAG 2.1 AA-aligned (Fluent defaults; **no** formal audit)
- **Persona switcher:** Always visible, top-right of app shell, replacing standard profile menu, searchable dropdown with recents and role groups
- **Vignette entry pattern:** Navigate as the persona — no special demo launcher

### 3.4 Persona switcher (locked architecture)
- **Architecture:** Persona overlay everywhere; **no real-auth switching beats**. One demo super user signs in once per session.
- **Personas in switcher:** User-pickable from the **full population** (any patient/HCP/internal-user). Includes an **"Anonymous Visitor"** pseudo-persona for V1's public-area beats.
- **Persona context attributes:** `id, name, role, avatarInitials, primaryAccountId, primaryPatientId, title, themeAccent`
- **Persistence:** localStorage so refresh doesn't reset
- **Hero rotation:** Weighted-random pick on each refresh (avoids repeats; deterministic after seeding)
- **Token-expiry safeguards:**
  - Pre-demo checklist item on Demo Health page ("Sign in fresh")
  - Auth-health indicator (green/yellow/red) on the switcher widget
  - Silent token refresh attempt on each persona switch
- **Audit-trail framing in script:** One-line "demo-only attribution" note + subtle "Demo mode" banner on every screen

### 3.5 Auth model
- **Pages identity provider:** single demo super user via Entra ID
- **Auth/role config retained** for completeness (architecture diagrams + governance doc); not exercised live in vignettes
- **No real auth beats** in any vignette
- **Auth credibility recovery:** None — accept the gap; rely on diagrams + governance doc

### 3.6 Multi-user (alternates)
- **Flavor A** — multiple alternates, one demos at a time, share the same data
- `SUPER_USER_UPNS` is an array; `install.ps1`/`upgrade.ps1` loops and assigns the same security roles to each
- **No primary** super user — all equal
- Helper scripts (planned for Phase 0 stubs, fleshed out later): `Add-DemoUser.ps1`, `Remove-DemoUser.ps1`, `List-DemoUsers.ps1`, `Test-DemoUser.ps1`

### 3.7 Connection ownership (hybrid)
- **Default for new connection references: service principal** via Microsoft Graph (where supported)
- **Reserved for interactive identity** (any super user signed in at the time):

### 3.8 Persona attribution in data
- **`cch_CreatedByPersona` and `cch_ModifiedByPersona` columns** on all audit-relevant tables (Patient, HCP, Account, Prescription, Shipment, Complaint, ServiceCase, SampleOrder, TrainingRecord, plus any flow-write target).
- Populated by the React layer at write time; readable by V4 triage, activity timelines, and the audit beat.
- **These are part of the initial schema**, not a migration (decision: pre-deployment plan changes update the schema definition, not the migrations folder; migrations only kick in after the first tagged release).

### 3.9 Evergreen design (data must always look "fresh")
- **Anchor-and-offset seed pattern:** seeds store offsets (e.g., `registeredDaysAgo`); compute `now - offset` at runtime. Single source of offsets in `data/offsets.ts`.
- **`cch_DemoAnchor` singleton table:** `LastRefreshedOn`, `Notes`. Refresh flow writes; UI banners read.
- **Daily scheduled refresh flow** at **5:00 AM Eastern**. Slides every time-sensitive field forward by elapsed delta. **Silent** (no audit log).
- **Per-vignette reset flows** (cloud-only, no laptop dependency).
- **Demo Health page** (in Code App) with: last refresh, oldest record, freshness traffic light, one-click "Refresh now," on/off toggle for the Live Sim, "Inject complaint (V4 hero)" button, "Run smoke tests" button, "Run doctor" link, last 10 deploys.
- **Live-events simulator flow:** every **10 minutes** during **Mon–Fri 8 AM–6 PM Eastern**, drops in new complaint/shipment update. Toggleable from Demo Health.
- **MDR-clock complaint (V4 hero):** reset to fixed urgent value (~18 hours remaining) on every refresh — always tense, never expired.
- **Stable identities:** patient/HCP/account names persist across refreshes; only dates/statuses/heroes rotate.
- **Calculated columns** in Dataverse for derived display (`IsOverdue`, `DaysSinceCreated`).
- **Templated agent-grounding docs:** authored in Markdown with `{{ today }}`, `{{ current_quarter }}` variables; rendered to **PDF + Word** and republished to SharePoint by a weekly flow.

### 3.14 Installability (the big "any SE can deploy this" requirement)
- **Single `scripts/install.ps1`** is the SE-shared engine, also called by the personal CI deploy (with `-NonInteractive`)
- **Modes:** `install | upgrade | uninstall | doctor | seed | refresh-dates`
- **Default mode in personal CI:** `upgrade`
- **Demo runs 100% in Power Platform + M365 cloud at runtime.** No external Azure resources, no laptop-hosted services, no `localhost` URLs in any flow/agent/app/site. CLIs are build-time only.
- **No mocked external APIs.** External carrier dropped in favor of in-platform `cch_Shipment` table + flow-driven lifecycle.
- **Vignette resets** are Power Automate flows (cloud-only), not local scripts.
- **Connection References + Environment Variables become a *requirement* in every flow and agent action.** This is a Phase-0 discipline, not a Phase-6 cleanup.
- **Auto-create on install:** Entra app registration(s); SharePoint site + libraries; Teams team + channel.
- **Generated but never auto-applied:** DLP policy script; Managed Environment opt-in script.
- **List + prompt:** installer lists Power Platform environments and prompts for target. Option to create new env if user has rights.
- **Consent handling:** pause and prompt inline at each consent point, validate the response, provide an option to skip and remind at the end.
- **Deployment settings:** JSON file (`scripts/deployment-settings.json` — gitignored; template is `deployment-settings.json.template`) the importer edits before running install. JSON Schema at `deployment-settings.schema.json` for editor validation.
- **Prereq checking:** auto-install missing prereqs where possible (PowerShell modules) with confirmation per module.
- **Uninstall scope:** user picks; defaults to Solution + App regs + SharePoint site + Teams team. Does NOT default to Demo super user delete or DLP/ME removal. `--yes-to-all` flag for scripted use.

### 3.15 Lifecycle modes & migrations
- **`install`** — first-time, provision everything. Once per env.
- **`upgrade`** — most-frequent. Solution upsert, code app push, Pages re-publish, agent re-publish, schema migrations, idempotent re-provision (skip what exists), insert-only seed updates by default. Default mode in CI.
- **`uninstall`** — manual, interactive selection.
- **`doctor`** — read-only health check. Reports drift; never changes data.
- **`seed`** — re-seed with optional reset.
- **`refresh-dates`** — run the demo-date refresh flow on demand.

### Migration framework
- **Numbered `.ps1` migration files** in `solutions/ContinuumHealthDemo/migrations/`. Each declares metadata: name, version, destructive boolean, description.
- **`0001_baseline.ps1`** — no-op other than stamping `cch_DeploymentVersion`. First **real** migration is `0002_*` whenever the first post-release schema change happens.
- Current deployed version stored in `cch_DeploymentVersion` env var.
- Full audit trail in `cch_DeploymentHistory` table (every install/upgrade event).
- **Forward-only rollback** — `doctor` reports drift, you fix, you re-run `upgrade`. No snapshot/restore.

### Upgrade behavior
- **Seed default:** insert net-new fixture rows only; never touch existing rows. `--reseed` flag wipes + reseeds.
- **Agent re-publish:** only if agent version changed. `--force-agents` flag overrides.
- **Destructive changes:** prompt before in interactive mode; require `-AllowDestructive` flag in non-interactive (CI). Migrations that drop columns/data must declare themselves destructive in their header.
- **Pre-upgrade summary** printed for confirmation: solution version delta, migrations to run (and how many destructive), agents to republish, new env vars needing values, connection refs needing binding.

### 3.16 CI / release
- **Tier 1 (every PR, ~30s):** lint, format, type-check, JSON schema validation, solution structure check (naming, env-var presence, no inline secrets, all flows use Connection References), migration order check, PowerShell syntax check, YAML lint, markdown lint, secret scan (gitleaks), Conventional Commits PR title check.
- **Tier 3 nightly + manual workflow_dispatch:** install → seed → smoke → uninstall (or `upgrade` against the long-lived `pp-demo-ci` env, your case). Reuses long-lived CI environment in place. ~15 min.
- **Personal `deploy.yml`:** `workflow_dispatch` only. Inputs: target env, what to deploy (everything/solution/seed/agents/pages/app), reset data, refresh dates, smoke tests, version/git ref. Defaults all to safe upgrade with smoke tests.
- **Auth in CI:** SP client secret in GitHub Actions secrets (`PP_SP_TENANT_ID`, `PP_SP_CLIENT_ID`, `PP_SP_CLIENT_SECRET`). OIDC federated identity is a future migration option.
- **No GitHub Environment protection** on personal deploy — `workflow_dispatch` click is the confirmation.
- **Personal env provisioning:** pre-create env + Entra app regs + SharePoint + Teams + super user **once**; CI only deploys app/data + runs `upgrade`.
- **Workflow output:** HTML summary on the run page (URLs, timings, smoke results) + install logs uploaded as workflow artifact.
- **Fork safety:** not enforced — README notes CI workflows reference repo-only secrets.
- **Release strategy:** `main` is always demoable + tagged releases at milestone points (`v0.1.0` Phase 1, `v0.2.0` Phase 2, …, `v1.0.0` full demo). Conventional Commits → auto-generated `CHANGELOG.md` (e.g., release-please action).

### 3.17 Testing strategy (minimum viable subset)
- **Tier 1 PR + pre-commit:** static checks (lint, format, types, JSON schema, secret scan).
- **`doctor.ps1`** — anytime, read-only, all-categories drift report.
- **Smoke tests** — bundled into `install.ps1`/`upgrade.ps1`, also exposed via `Run smoke tests` on Demo Health page. ~Per-table read, per-agent Direct Line ping, per-flow manual-trigger ping, per-Pages-page HTTP ping.
- **One Playwright E2E per vignette** — Tier 3 nightly.
- **Unit tests for the dangerous bits** — migration runner, persona switcher, anchor-and-offset math (Vitest + Pester 5).
- **Direct Line ping per agent** — bundled in smoke.
- **Coverage targets:** none enforced. Tests encouraged, not gated.
- **Pre-commit hooks:** formatting + lint only (fast, sub-2-second). Auto-installed by `npm install`.
- **Test data isolation:** tagged test rows (`cch_TestRun = true`) + live-sim toggled off during E2E.
- **Demo Health page surfaces doctor + smoke results.**
- **Frameworks:** Vitest, Playwright, Pester 5, Direct Line API helpers (custom JS), ajv-cli, PSScriptAnalyzer, markdownlint-cli2, gitleaks. **Skip:** React Testing Library (Vitest renders components fine for the few UI tests we'll write), heavy unit-test coverage on UI components, snapshot tests, axe-core in CI, snapshot-and-restore of solution state.
- **Squad gains a Tester role** — writes tests as a side effect of building each feature; never as a separate phase. Owns `doctor.ps1`, smoke suite, and the Tier 1 + Tier 3 GitHub Actions workflows.

## 4. Data model (Dataverse — solution `ContinuumHealthDemo`, prefix `cch_`)

### Custom tables (initial schema, authored in Phase 1)
- **Patient** — name, DOB, MRN (synthetic), plan, primary HCP (lookup), assigned device (lookup), status, registration date, contact info, etc.
- **HCP** — name, NPI (fake), specialty, organization (lookup), credentialing status

- **Complaint** — patient, device, severity, narrative, MDR-reportable flag, AI-generated summary, triage status, agent fields (see Section 4.1), MDR clock
- **ServiceCase / ReplacementRequest** — patient, original device, reason, replacement device, status
- **TrainingRecord** — HCP or system user, product, date, certification status
- **SampleInventory** — rep (sysuser), sku, qty, location
- **SampleOrder** — created by FCS or by Enablement Agent; rep, account, HCP, sku, qty, status
- **DemoAnchor** (singleton) — `LastRefreshedOn`, `Notes`
- **LiveSimSetting** (singleton) — toggle + cadence override + window override

## 6. Copilot Studio agents (3, final lineup)

### 6.1 Patient Support / Persona-Aware Agent
- Used in V1 (Pages floating bubble), V2 (HCP daily-briefing card on dashboard), V3 (Code App docked panel)
- Persona-aware via conversation variables: `personaId, personaRole, personaName, primaryAccountId, primaryPatientId`
- Topics branch on `personaRole` (Patient | HCP | FCS | Anonymous)
- V1 capabilities: troubleshoot sensor problem, request replacement (calls flow), check order status, FAQ from product docs, schedule clinician callback, file a complaint
- V2 capability: HCP daily briefing ("you have N patients needing attention")
- V3 capabilities: summarize an account, draft Outlook email follow-up (in-app preview only — locked V3 decision), post Teams channel update (real channel post + brief Teams switch-over), answer training/product questions, order sample inventory, submit complaint on behalf of account

### 6.2 Quality Triage Agent (V4 only — autonomous + analyst Q&A)
- Triggered start point: Dataverse `cch_Complaint` row create
- Tools: read complaint, read device history, read related complaints, write triage fields, write MDR draft, post Teams adaptive card, update status
- Knowledge: MDR template, complaint classification taxonomy, regulatory glossary
- Topics in docked chat: "Why MDR-reportable?", "Show me other complaints on this lot", "Re-run triage with this added context", "Summarize this case for me"
- Connection: SP via Graph for Teams; SP for Dataverse

### 6.3 Continuum Enablement Agent (V5 + V6)
- Distinct from #1 and #2; published to multiple surfaces
- Knowledge sources (SharePoint, all generated by templated-doc flow):
  - Product manuals — Continuum CGM G7, G7 Pro, sensor accessories
  - Competitive briefs — Contoso vs. fictional "Adventurer Glucose Inc."
  - Internal policies — sample handling, expense, training mandates
  - Regulatory glossary + MDR template (shared with V4 Quality agent)
  - Training catalog
  - Product launch FAQs
- Tools (Power Automate flows):
  - Order samples (creates `cch_SampleOrder` + Teams Adaptive Card)
  - Schedule training (creates `cch_TrainingRecord` + Teams Adaptive Card)
  - Look up regulatory clock (knowledge-only)
  - Look up internal policy (knowledge-only)
